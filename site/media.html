Approach · for anyone who ships beyond a screen

One declaration, ten channels, and what each one can carry.

A channel is where a declaration is carried: a screen, a voice, a printed page, a lamp, a machine reader. The language declares what a person is doing once; a channel that cannot carry something the declaration promises is refused by name, before anything is drawn, spoken or printed. A channel is what the language and the law call a medium.

What a channel is made of

The ten channels are a closed list, so a map of what a person can do in each is finite. They are described by properties and not by taste, so a new one is classified and not argued about: whether the rendering stays, whether the person can choose their order through it, whether they chose to attend, how much meaning arrives in a glance, and whether it can be withdrawn once made. That last property is what separates a rendering from an actuation, and the reason print and signage behave unlike a screen.

In a declaration the keyword is SURFACE_AS and the diagnostics say medium; the data file is media.json. None of those words change. Sensors and actuators are not channels: they render nothing, and reach a person only when something else renders them. The coverage of the law across these channels is the grid.

Native, degraded, absent

For each of the 22 verbs, each channel is recorded as native (it serves the intent naturally), degraded (served at a cost the designer must know, such as a parallel act becoming a serial one) or absent (no analogue exists, so a surface declaring only this channel cannot satisfy the intent). Only absent raises a diagnostic. Degraded is data for tools and designers, because a warning that fired on every serial surface would be noise and not law.

Limit: the carriage is a first cut. It was derived by reasoning about each channel's properties and not by rendering anything, and the lines for auditory, voice and haptic are the ones most likely to move on contact with a real surface.

One declaration, two channels

A phone line cannot zoom. A person asking for their balance by voice, in a flow that promises ZOOM, has been promised something the channel cannot carry:

DEFINE VIBE phone_line (
  SURFACE_AS voice,
  MOTION none
)
DEFINE INTENT_FLOW check_balance (
  SATISFIES [UNDERSTAND, ZOOM],
  ALWAYS_REACHABLE [CANCEL, EXIT],
  ACTOR caller
)
$ node tools/zui/cli.js check check_balance.zui
check_balance.zui:5  error  VERB_NOT_CARRIED  ZOOM in check_balance on voice
    A declaration satisfies, or promises to keep reachable, an intent the declared medium cannot carry at all.
    Rule 82 · Perceivable State · Article II

1 error(s), 0 warning(s) across 1 file(s) at level 2

The same flow on a screen carries it, and is clean:

DEFINE VIBE screen_page (
  SURFACE_AS visual,
  MOTION none
)
DEFINE INTENT_FLOW check_balance (
  SATISFIES [UNDERSTAND, ZOOM],
  ALWAYS_REACHABLE [CANCEL, EXIT],
  ACTOR caller
)
$ node tools/zui/cli.js check check_balance_screen.zui
clean — 1 file(s), 0 violations at level 2 against Zui v3.13

Both runs are re-run by the site's own check. A refusal here is a refusal of a promise, not of the voice line: the declaration is lawful in a voice if it asks for what a voice can carry.

What the proof says, and what it does not

The sentence the design rests on is one declaration, many renderings, one law. The instrument for it does not assert that two renderings match: they are irreducibly different. It asserts that every difference between them is one the published data already predicted. A difference the data accounts for is the model working; a difference it does not is drift, and fails the run. Run on the suite's two cases it says:

$ node tools/zui/cross-medium.js

    signals      3 declared
    differences  3 total · 0 predicted · 3 undecided · 0 drift

      signal danger: signal.json records no rendering for print, so this value is unproved rather than wrong
      signal muted: signal.json records no rendering for print, so this value is unproved rather than wrong
      signal warning: signal.json records no rendering for print, so this value is unproved rather than wrong

  invoice-review.zui  —  visual vs auditory
    intents      5 declared · 5 carried by both
    signals      3 declared
    differences  5 total · 5 predicted · 0 undecided · 0 drift

  no drift, and 3 difference(s) the data cannot yet speak to.
  Nothing here is wrong. The central claim is NOT PROVED for these pairs,
  and it will not be until the silent channel records what it renders.

So the claim is proved for one pair and not proved for the other. Screen against sound has five differences, all predicted. Screen against print has three the data is silent on, because the signal file records no rendering for print: that is unproved, not wrong, and the instrument exits non-zero rather than call it a pass.

Limit: nobody has perceived any of these channels. Two renderings that agree with the data can still both be wrong for a person, and no counter here can see it.
