Approach · for anyone who ships beyond a screen

Zane renders one declaration in ten channels, and describes each channel by what it can carry.

A channel is the medium, such as a screen, a voice, a printed page, a lamp or a machine reader, that carries a declaration to a user, a person or an agent, and the list of channels lets a tool check a declaration against what its channel can carry. The language declares what a user is doing once. The channel list prevents a declaration from promising what its channel cannot carry: the language refuses such a channel by name, before anything is drawn, spoken or printed. A channel is what the language and the law call a medium.

The ten channels and the properties that describe each channel

The ten channels form a closed list, so the map of what a user can do in each channel is finite. The channels are described by properties and not by taste, so a new channel is classified and not argued about. The properties are whether the rendering stays, whether the person can choose the order in which they take it in, whether the person chose to attend, how much meaning arrives in a glance, and whether the rendering can be withdrawn once it is made.

The last property separates a rendering from an actuation, and it explains why print and signage behave unlike a screen.

In a declaration the keyword is SURFACE_AS, the diagnostics say medium, and the data file is media.json; none of these words change. Sensors and actuators are not channels: they render nothing, and they reach a user only when something else renders them. The grid page shows how the law covers these channels.

How each channel carries each verb: native, degraded or absent

For each of the 22 verbs, each channel is recorded as native, degraded or absent. A native channel serves the intent naturally. A degraded channel serves the intent at a cost the designer must know, such as a parallel act becoming a serial one. An absent channel has no analogue for the intent, so a surface that declares only this channel cannot satisfy the intent.

Only absent raises a diagnostic. Degraded is data for tools and designers, because a warning that fired on every serial surface would be noise and not law.

Limit: the carriage is a first placement. It is derived by reasoning about each channel's properties and not by rendering anything, and the lines for auditory, voice and haptic are the most likely to change when they are tested on a real surface.

One declaration checked in two channels, refused in voice and clean on a screen

A phone line cannot zoom. A flow in which a user asks for their balance by voice, and which promises ZOOM, promises something the voice channel cannot carry:

DEFINE VIBE phone_line (
  SURFACE_AS voice,
  MOTION none
)
DEFINE INTENT_FLOW check_balance (
  SATISFIES [UNDERSTAND, ZOOM],
  ALWAYS_REACHABLE [CANCEL, EXIT],
  ACTOR caller
)
$ node tools/zane/cli.js check check_balance.zane
check_balance.zane:5  error  VERB_NOT_CARRIED  ZOOM in check_balance on voice
    A declaration satisfies, or promises to keep reachable, an intent the declared medium cannot carry at all.
    Rule 82 · Perceivable State · Article II

1 error(s), 0 warning(s) across 1 file(s) at level 2

The same flow on a screen carries ZOOM, and the check finds it clean:

DEFINE VIBE screen_page (
  SURFACE_AS visual,
  MOTION none
)
DEFINE INTENT_FLOW check_balance (
  SATISFIES [UNDERSTAND, ZOOM],
  ALWAYS_REACHABLE [CANCEL, EXIT],
  ACTOR caller
)
$ node tools/zane/cli.js check check_balance_screen.zane
clean — 1 file(s), 0 violations at level 2 against Zane v3.15

The site's own check re-runs both runs. The refusal applies to the promise and not to the voice line: a declaration is lawful in a voice channel when it asks only for what a voice can carry.

What the cross-channel instrument proves, and what it does not prove

The design rests on the sentence one declaration, many renderings, one law. The instrument that tests this sentence does not assert that two renderings match, because two renderings are irreducibly different. It asserts that every difference between them is one the published data already predicted.

A difference that the data accounts for shows the model working, and a difference that the data does not account for is drift and fails the run. On the suite's two cases the instrument reports:

$ node tools/zane/cross-medium.js

Cross-medium conformance — 2 case(s)
  media        10 enumerated, matrix v1.1
  signals      5 values, vocabulary v1.3

  invoice-review.zane  —  visual vs print
    intents      5 declared · 5 carried by both
    signals      3 declared
    differences  3 total · 0 predicted · 3 undecided · 0 drift

    UNDECIDED — nothing is contradicted; the data is silent, so this pair is not proved:
      signal danger: signal.json records no rendering for print, so this value is unproved rather than wrong
      signal muted: signal.json records no rendering for print, so this value is unproved rather than wrong
      signal warning: signal.json records no rendering for print, so this value is unproved rather than wrong

  invoice-review.zane  —  visual vs auditory
    intents      5 declared · 5 carried by both
    signals      3 declared
    differences  5 total · 5 predicted · 0 undecided · 0 drift

  no drift, and 3 difference(s) the data cannot yet speak to.
  Nothing here is wrong. The central claim is NOT PROVED for these pairs,
  and it will not be until the silent channel records what it renders.

The claim is therefore proved for one pair of channels and not proved for the other. Screen against sound has five differences, and the data predicts all five. Screen against print has three differences on which the data is silent, because the signal file records no rendering for print. These differences are unproved and not wrong, and the instrument exits non-zero rather than report a pass.

Limit: nobody has perceived any of these channels. Two renderings that agree with the data can still both be wrong for a person, and no counter here can detect it.
