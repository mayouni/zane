Use · for a team with an iOS or Android application

Zane checks a mobile app through the declarations of its screens and a screenshot audit, because a mobile app has no page to measure.

The mobile workflow checks an iOS or Android application, which has no markup for the UI audit to read, with two tools: the language checks what the screens declare, and a screenshot audit judges facts reduced from an image against the three rules a screenshot can decide. The workflow lets a team check the declared flows of a phone app, and it prevents a screenshot from passing a rule that a screenshot cannot decide. The language check runs today. The screenshot audit has never been run on a real application.

A made-up example of a mobile payment flow, checked by the verifier

This case is made up. No mobile application was chosen, and none has been run through the screenshot audit. The flow below is a typical one-tap payment, written to show what the verifier decides about the declaration of a mobile flow. This case is not a finding about anybody's product.

A phone screen that pays on one tap turns selection into execution: the person points, and money moves. In the language this flow is a selection that acts without a confirmation, and the verifier refuses it:

DEFINE INTENT_FLOW tap_to_pay (
  SATISFIES [SELECT, ACT],
  ALWAYS_REACHABLE [UNDO, CANCEL, EXIT],
  ACTOR customer
)
$ node tools/zane/cli.js check tap_to_pay.zane
tap_to_pay.zane:1  error  SELECT_ACT_COLLAPSE  tap_to_pay
    Selection has become execution: SATISFIES holds SELECT and ACT without CONFIRM.
    Rule 16 · Intentional Clicks · Article II

1 error(s), 0 warning(s) across 1 file(s) at level 2

The law asks the flow to declare a confirmation, which on a phone is a second tap or a held press, and the declaration below passes:

DEFINE INTENT_FLOW tap_to_pay (
  SATISFIES [SELECT, CONFIRM, ACT],
  ALWAYS_REACHABLE [UNDO, CANCEL, EXIT],
  ACTOR customer
)
$ node tools/zane/cli.js check tap_to_pay_confirmed.zane
clean — 1 file(s), 0 violations at level 2 against Zane v3.14

The screenshot audit and the three rules it decides

For an application with no page to read, a writer reduces a screenshot to facts (each line of text, its box and the luminances behind it), and an audit judges the facts. The audit decides three rules and nothing else: Rules 62 and 105 for contrast against a floor, and Rule 107 for the size of text. Every other rule reads not audited, never passed, and a measurement that could be wrong at its worst end (a photographic background) is never a pass. A script that needs nothing installed checks the shape of the facts file, its arithmetic and the decisions. Below, the script runs on the example file that ships with it, which is made by hand:

$ node doc/design/audit/check-facts.js doc/design/audit/example.facts.json
3 lines found; text the OCR did not find is not audited

L1 "Overdue balance"
  contrast (rules 62, 105)  fail        2.85:1 is below 4.5:1
  size floor (rule 107)     fail        the line box is 9 pt, so the font is at most that: below the 12 pt (16 CSS px) floor
L2 "Account summary"
  contrast (rules 62, 105)  pass        12.63:1 is at least 4.5:1, background uniform
  size floor (rule 107)     not_decided a 18 pt line box does not show the font is large: line height can be generous around small text
L3 "Quarterly results"
  contrast (rules 62, 105)  not_decided 4.66:1 at the typical background but 2.59:1 at the worst end (background 0.1753 moved 0.18 toward the text colour): never a pass
  size floor (rule 107)     not_decided a 18 pt line box does not show the font is large: line height can be generous around small text

NOT AUDITED: every rule other than 62, 105, 107 (rule 105 only for its contrast half). A screenshot does not decide them, and "not audited" is not "passed".
PROJECTED, NOT VERIFIED BY A PERSON (CENTRAL-PERCEPTGATE-01): nobody looked at the screenshot these facts describe.

doc/design/audit/example.facts.json: valid; 3 line(s)

The example has three lines. The first fails on contrast and on size, the second passes on contrast and cannot be decided on size, and the third is never a pass because its background moves toward the text at the worst end. The third line shows the purpose of the design: an uncertain measurement is never a pass.

Which parts of the mobile workflow run today, and which do not

  • Two parts run today: the verifier on a mobile flow's declaration, shown above, and the checker of the facts file with its three decisions.
  • One part has never run: the writer that reduces a real screenshot to facts, on a real application. The capture loop is a separate part and is not built. This page therefore cannot show a real mobile run, and it says so rather than show a made-up one.
  • No person has looked at the screenshot. The facts describe a screenshot that no person has looked at, and the checker prints that on every run.

Limit: a real case needs an application and its owner's agreement. Until someone names such an application, the second half of this workflow is designed and not run.
