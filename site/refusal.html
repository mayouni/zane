Language · what the verifier refuses

A refusal is the verifier's verdict on a declaration that breaks the law, and it names the line, the rule and the right it rests on.

A refusal is what the verifier returns instead of clean when a declaration breaks the law, and it states where the declaration is wrong, what is wrong and which rule forbids it. Refusals ensure that a no always carries its reasons, so a person can trace every refusal back to the law. The verifier has 37 diagnostics. This page shows one real refusal, its lawful twin, the envelope any tool can read, and what the diagnostics cannot decide.

One refusal of a declaration, explained line by line

The declaration below describes a three-step account opening in which the person can undo a step and cancel the step, but has no way to leave the whole flow.

// A three-step wizard. The person can undo and cancel, but not leave.
DEFINE WIZARD account_opening (
  SATISFIES [UNDERSTAND, CONFIRM, ACT],
  ALWAYS_REACHABLE [UNDO, CANCEL],
  STEPS [identity, funding, review],
  ACTOR applicant
)
$ node tools/zane/cli.js check account_opening.zane
account_opening.zane:2  error  TRAPPED_FLOW  account_opening
    A multi-step flow has no reachable EXIT.
    Rule 51 · The Cognitive Tunnel · Rule 53 · Interaction Lockdown · Article II · the right to leave

1 error(s), 0 warning(s) across 1 file(s) at level 2
  • The line and the subject (account_opening.zane:2, account_opening) say where the defect is, so an editor can jump to it.
  • The code (TRAPPED_FLOW) is stable forever. A retired code is never reused, so a rule written against a code keeps its meaning.
  • The sentence says what is wrong in terms of the declaration, not in terms of any screen.
  • The citation says why the declaration is wrong: it names two rules of the law, the article they serve, and the right of the person that is at stake. The verifier issues no refusal that cannot say why.

The verifier exits with code 1, which is all a CI gate needs. The same declaration with a way out is clean:

// The same wizard with a way out.
DEFINE WIZARD account_opening (
  SATISFIES [UNDERSTAND, CONFIRM, ACT],
  ALWAYS_REACHABLE [UNDO, CANCEL, EXIT],
  STEPS [identity, funding, review],
  ACTOR applicant
)
$ node tools/zane/cli.js check account_opening_exit.zane
clean — 1 file(s), 0 violations at level 2 against Zane v3.14

The two declarations form a twin: they differ by one change, and the verdict flips. The suite holds 22 twins, so that the law is tested against what it must allow as well as against what it must refuse. The site's own check re-runs the terminal output above, so the page cannot drift from the verifier.

The same refusal as a JSON envelope that any tool can read

Every court in the family writes its refusals in one envelope, so one CI step, one editor plugin or one dashboard can read all of them. With --json the refusal above is this object, which is the contract's six fields plus the level and the subject the Zane court adds:

$ node tools/zane/cli.js check account_opening.zane --json
{
  "code": "TRAPPED_FLOW",
  "severity": "error",
  "message": "A multi-step flow has no reachable EXIT.",
  "span": { "file": "account_opening.zane", "line": 2 },
  "cites": ["rule:51", "rule:53", "article:intent", "right:leave"],
  "language": "zane",
  "level": 2,
  "subject": "account_opening"
}

The shape of the envelope is a JSON schema in doc/diagnostic-contract.schema.json, and a court that emits the envelope validates against that file. The human text above names the article by its title, and the envelope names the same article by its identifier.

What the verifier can decide at each level, and what each level needs

Each diagnostic belongs to a level, and the level states what the verifier must be given before it can decide. Below level 3 the declaration alone is enough. From level 3 upward, the verifier needs facts that a declaration does not hold, and without those facts it says nothing, and never says clean.

LevelIt needsDiagnosticsFixtures
1 · Formnothing but the file1012
2 · Local meaningnothing but the file2256
3 · Across the surfacea symbol table you supply: entities, actors, state45
4 · Painteda rendered surface10

The fixture counts are the files in the suite that exercise each level. At level 4 a diagnostic is defined, and nothing in the suite can yet exercise it, because a rendered surface is not a file. The reference verifier stops at level 2 unless it is given a table.

A declaration cannot say whether a page looks right, or whether a person understood it. The audit measures some of these questions after painting, and only a person can answer the rest; the four steps describe where each check applies.

Diagnostics that cite no rule of the law, and why

Of the 37 diagnostics, 17 cite at least one rule, 8 cite an article but no rule, and 12 cite nothing. The twelve that cite nothing are about the form of the file: a misspelling, a duplicate, or a name or value that is not in a closed list.

These twelve say that the file is not yet a declaration, and they do not say that a person is harmed. The eight that cite only an article mark places where the law states a principle and has no rule narrow enough to point at.

The grounding of the diagnostics is therefore incomplete, and this page states the gap as a number rather than hiding it. A diagnostic that cites a rule can be traced to its reasons, and a diagnostic that cites no rule can be trusted only as far as the grammar.
