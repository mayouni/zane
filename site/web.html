Use · for a team with a web application already in production

Zane checks a web application in production by declaring its surfaces, running the verifier and auditing its live pages.

The web workflow declares the surfaces of a web application that is already in production, checks the declarations with the verifier, and audits the pages a browser paints. The workflow lets a team check an application it already runs at the cost of a few hours, not a rewrite. The case on this page is the navigation of stzsite, the Softanza site, a real site in production that this project reads and does not own. This project only read the site, and the page reports this project's run, what the run cost and what it found.

The case: the navigation of the Softanza site

A web application already in production is the common case, and in this case a retrofit has to cost an afternoon and not a rewrite. The subject here is the navigation of stzsite, the Softanza site, which has a main menu of five entries, a start link and a language switch. The site is another desk's repository, which this project reads and never writes. The declarations below are Zane's description of pages it does not own, and the header of their file says so.

This case is one navigation on one site, read on 4 November 2026, and it shows the workflow and its cost. The declarations are written by hand from the pages, which is the workflow's first step.

How to declare the surfaces and run the verifier on them

The first step writes down, in the language, what the reader does on each surface. The first draft of the language switch declared that the switch acts and also that its role is to navigate, and the verifier refused the draft:

DEFINE NAV_GRAPH site_menu (
  SATISFIES [LOCATE, DISCOVER, UNDERSTAND],
  ALWAYS_REACHABLE [EXIT],
  VISIBLE_STATE [current_section, language],
  ACTOR reader
)
DEFINE INTERACTION language_switch (
  SATISFIES [ACT],
  ALWAYS_REACHABLE [UNDO, CANCEL],
  ROLE navigate,
  ACTOR reader
)
$ zane check stzsite_menu.zane
stzsite_menu.zane:10  error  ROLE_ACTS_WITHOUT_CONSEQUENCE  navigate language_switch satisfies ACT
    A control promising to change nothing declares that it acts.
    Rule 119 · A Card Is Not a Button · Rule 112 · Motion Reports, It Never Decorates · Rule 16 · Intentional Clicks · Article II

1 error(s), 0 warning(s) across 1 file(s) at level 2

The verifier here corrects the author: a control that changes what is shown, and changes nothing that is true, is not an act. The reading was wrong, and the site was not. The corrected declaration makes the switch a selection:

DEFINE NAV_GRAPH site_menu (
  SATISFIES [LOCATE, DISCOVER, UNDERSTAND],
  ALWAYS_REACHABLE [EXIT],
  VISIBLE_STATE [current_section, language],
  ACTOR reader
)
DEFINE INTERACTION language_switch (
  SATISFIES [SELECT],
  ALWAYS_REACHABLE [UNDO, CANCEL],
  ROLE navigate,
  ACTOR reader
)
$ zane check stzsite_menu_fixed.zane
clean — 1 file(s), 0 violations at level 2 against Zane v3.16

The checked-in file is examples/web-case/stzsite-navigation.zane, and it adds the third surface (the start page) and a header that says whose description it is. This site's own check re-runs both runs above.

How to run the UI audit on the live pages of another site

The UI audit measures what a browser paints, and it reads pages through same-origin frames, so it cannot audit a site served from another origin. For a site that you may only read, the smallest honest way past that limit is a read-only server that puts the other folder and the audit on one origin: examples/web-case/serve-beside.js. The server has forty lines, binds the local machine only, answers GET only and writes nothing.

The audit ran on six pages (the home page and the Platform, Vision, Learn, Reference and Zui pages), in the default mode, on 4 November 2026, the audit reported twenty-six findings. The findings are of two kinds, and only one kind is about the site:

  • Four findings concern Rule 108, the path. The Platform, Vision, Learn and Reference pages omit the visible trail, which the rule allows where an always-visible bar marks the page, but they carry no labelled navigation landmark for the path. The Zui page carries one and is clean.
  • Twenty-two findings concern contrast on the home page, and every one of them is text laid over the photograph. These findings are not about the site: the audit reads the colours of the elements behind a text and cannot see through a photograph or a text shadow. The site's own page says that it measures those words over the brightest part of the photograph, which is the right measure, and this audit does not take that measure.

The four findings are findings about the site. The twenty-two are a reason to measure text over a photograph at the photograph's brightest part, as the site's own page does.

Where each finding of the audit lands on the grid

A finding is filed so that it lands on a cell of the grid, and never as a new rule. The missing path landmark belongs to understand (where am I) on the visual channel, a cell with a rule written for it (Rule 108). The finding confirms the cell, and the audit's check for it shows the system working. The photograph contrast belongs to perceive on the visual channel, where the law also has rules. It is filed as a finding about the instrument, because the site's own measure is the right one. Neither finding extends the grid.

What the web workflow yields today, and what it asks of a team

  • The workflow yields three surfaces declared by hand, one real refusal of the author's own reading with its fix, and six pages audited with four findings that the site's owner can verify. It costs a few hours of reading and a forty-line server.
  • The workflow asks four things of a team: the surfaces declared by hand, the other site served beside the audit, text over a photograph measured at the photograph's brightest part, and the owner's agreement to each finding.
  • When a team's own application is the subject, the same steps apply and the team is the owner: the team declares the surfaces, runs the verifier, serves the application beside the audit and places each finding on a cell.

The single-file build of the tools, zane, replaces that server with one command: zane serve --app DIR serves the other site beside the audit (doc/design/BINARY.md).
