The case, and what it is

A web application already in production is the common case, and the one where a retrofit has to cost an afternoon and not a rewrite. The subject here is the navigation of stzsite, the Softanza site: a main menu of five entries, a start link, and a language switch. It is another desk's repository, read here and never written; the declarations below are StzZui's description of pages it does not own, and say so in their file's header.

Limit: this is one navigation on one site, read on 4 November 2026. It shows the workflow and its cost. It does not show how the law fares on a typical application, and the declarations are written by hand, because no importer from a page to a declaration exists.

Declare the surfaces, and run the verifier

Step one is writing down, in the language, what the reader does there. My first draft of the language switch said it acts and also that its role is to navigate. The verifier refused it:

DEFINE NAV_GRAPH site_menu (
  SATISFIES [LOCATE, DISCOVER, UNDERSTAND],
  ALWAYS_REACHABLE [EXIT],
  VISIBLE_STATE [current_section, language],
  ACTOR reader
)
DEFINE INTERACTION language_switch (
  SATISFIES [ACT],
  ALWAYS_REACHABLE [UNDO, CANCEL],
  ROLE navigate,
  ACTOR reader
)
$ node tools/zui/cli.js check stzsite_menu.zui
stzsite_menu.zui:10  error  ROLE_ACTS_WITHOUT_CONSEQUENCE  navigate language_switch satisfies ACT
    A control promising to change nothing declares that it acts.
    Rule 119 · A Card Is Not a Button · Rule 112 · Motion Reports, It Never Decorates · Rule 16 · Intentional Clicks · Article II

1 error(s), 0 warning(s) across 1 file(s) at level 2

That is the verifier doing its work on the author: a control that changes what is shown, and nothing that is true, is not an act. The reading was wrong, not the site. Corrected, it is a selection:

DEFINE NAV_GRAPH site_menu (
  SATISFIES [LOCATE, DISCOVER, UNDERSTAND],
  ALWAYS_REACHABLE [EXIT],
  VISIBLE_STATE [current_section, language],
  ACTOR reader
)
DEFINE INTERACTION language_switch (
  SATISFIES [SELECT],
  ALWAYS_REACHABLE [UNDO, CANCEL],
  ROLE navigate,
  ACTOR reader
)
$ node tools/zui/cli.js check stzsite_menu_fixed.zui
clean — 1 file(s), 0 violations at level 2 against Zui v3.13

The checked-in file is examples/web-case/stzsite-navigation.zui, with the third surface (the start page) and a header that says whose description it is. Both runs above are re-run by this site's own check.

Audit the live pages

The UI audit measures what a browser paints, and it reads pages through same-origin frames, so a site served from somewhere else cannot be audited from it. For a site you are only allowed to read, the smallest honest way past that is a read-only server that puts the other folder and the audit on one origin: examples/web-case/serve-beside.js, thirty-six lines, binding the local machine only, answering GET only, writing nothing.

Run on six pages (the home page and the Platform, Vision, Learn, Reference and Zui pages), in the default mode, on 4 November 2026, it reported twenty-six findings. They are of two kinds, and only one is a finding about the site:

  • Four findings on Rule 108, the path: the Platform, Vision, Learn and Reference pages omit the visible trail, which the rule allows where an always-visible bar marks the page, but carry no labelled navigation landmark for the path. The Zui page carries one and is clean.
  • Twenty-two findings of contrast on the home page, every one of text laid over the photograph. These are not findings about the site: the audit reads the colours of the elements behind a text and cannot see through a photograph or a text shadow. The site's own page says it measures those words over the brightest part of the photograph, which is the right measure, and which this audit does not take.

Limit: the audit passes what it cannot see through and flags it by the wrong reasoning; both directions are limits of the instrument, and the second is the same one this site's own front page has. Read the four as findings, and the twenty-two as a reason to measure over the photograph.

Place each finding on the grid

A finding is filed so that it lands on a cell of the grid, and never as a new rule. The missing path landmark is understand (where am I) on the visual channel, a cell with a rule written for it (Rule 108): it confirms the cell, and that the audit has a check for it is the system working. The photograph contrast belongs to perceive on the visual channel, where the law has rules too; it is filed as a finding about the instrument, since the site's own measure is the right one. Neither extends the grid.

What this yields today, and where it stops

  • Yields: three surfaces declared by hand, one real refusal of the author's own reading and its fix; six pages audited with four findings the site's owner can verify; the cost, a few hours of reading and a thirty-six-line server.
  • Stops: nothing reads a page into a declaration; the audit needs the other site served beside it; the audit cannot see through photographs, so a site with a hero image gets false findings or none; and the owner's agreement is not part of any of this.
  • If a team's own application is the subject, the same steps apply and the owner is the team: declare, run, serve the application beside the audit, place each finding on a cell.

The single-file build of the tools, designed in doc/design/BINARY.md, would replace that server with one command. It is not built.
