Why · Comparison · for people who build with a framework, or know the languages that describe an interface

Four UI frameworks build an interface and five description languages describe one, and this page compares each with Zane from its own published page.

A UI framework builds the screen and a description language describes an interface in a notation tools can exchange, and this page states what each framework and language decides and when, what Zane takes from it and what Zane adds. The comparison lets a developer see which decisions stay with the framework or the language and which checks a Zane declaration adds before a screen exists. The framework rows have been checked by a second reading of the projects' own documentation.

The four UI frameworks that build the screen, compared with Zane

The four frameworks build the screen. They are compared on what each says of itself, and they do not compete with a declaration: a surface declared in Zane could be built in any of them, and this page does not claim that any integration exists.

Name, and its pageWhat it decides, and whenWhat Zane takesWhat Zane adds
React
react.dev		 Presented as a way to build an app from components: JavaScript functions that return markup, nested, fed data as props and kept current by state. The page sets rules for writing a component (names, closed tags, where a hook may be called) and says nothing of accessibility. The habit of describing a screen from data and state, and not commanding it. A declaration of what the user, a person or an agent, is doing, one level above the component tree. React documents lint rules for its own Rules of React; none of the cited pages is about whether the user can leave or undo.
SwiftUI
Apple documentation, get started		 Described as declarative programming for an app's interface and behavior on every Apple platform: the developer writes the outcome wanted and SwiftUI builds the interface from it. (Apple's documentation pages build themselves in the browser, so this rests on its get-started page and its overview as search returns it.) Writing the outcome and not the steps; the idea that a view describes a state. A statement of the intent behind the outcome, and a law that can refuse it. The cited SwiftUI pages describe no check of that kind; a WWDC session describes a separate accessibility audit that checks a rendered screen when tests run.
Jetpack Compose
developer.android.com		 Android's recommended toolkit for native interfaces: Kotlin functions describe what the screen should look like, and it updates when state changes. Its course covers accessibility and testing beside layout, theming and state. Accessibility and testing placed beside the way a screen is built, not after it. Compose documents accessibility checks that run in tests on a rendered interface (labels, contrast, touch-target size) and lint checks. Zane adds rules about what a user must be able to do, as data a tool can load before a screen exists.
Flutter
flutter.dev		 Presented as an open-source framework for natively compiled apps on several platforms from one codebase, written in Dart. The front page does not say how an interface is described in it; its documentation describes the framework as declarative. One description carried to several platforms, which is the same ambition as one declaration for several channels. A refusal when a promise cannot be carried: a verb a platform or channel lacks is refused by name. Flutter's documentation offers accessibility guidelines for widget tests (contrast, target size, labels); none of the cited guidelines refuses a promise a platform cannot keep.

Checked by a second reading of the projects' documentation. A second reader, given only these rows and the projects' own links, marked each cell as agreeing, overstated or wrong. The second reader found one overstated cell, SwiftUI's, whose claims went past the pages that could be read. The second reader also found that each framework's own documentation ships accessibility or lint checks that the first wording left out, and the cells now say so. The second reader is not a person who builds with these frameworks. Apple's documentation pages render in the browser, so the SwiftUI row still rests on an overview and a search, and Compose's "Kotlin functions" clause is not independently confirmed.

The description languages that describe an interface, from task models to SCXML

The description languages describe an interface, a form, a dialog or a state machine, in a notation that tools can exchange. Two of them, VoiceXML and SCXML, come from a working group that also made the standards for speech, and one, UIML, comes from a different body. The model-based work is the closest relative of Zane.

Name, and its pageWhat it decides, and whenWhat Zane takesWhat Zane adds
Task models and abstract interfaces
W3C task models, abstract UI, ConcurTaskTrees		 The nearest ancestors. ConcurTaskTrees is a notation for task models; the W3C working group's notes define task models and abstract interface models independent of platform. The group closed in 2014 and its notes are off the standards track. Describing the interface above the widget, in a form tools exchange. None of the cited pages states a law of rights as data, refuses a declaration by name, or ships a suite that any implementation can run. Zane also closes the channel axis to ten, with what each can carry.
UIML 4.0
OASIS		 A vendor-neutral meta-language for a user interface, whose vocabulary of parts, properties and events is defined outside the specification (Committee Specification, 2009). A description that does not depend on one interface metaphor. The law and the verifier. UIML describes an interface; Zane declares what the user must be able to do and refuses a declaration that does not allow it.
XForms 1.1
W3C Recommendation, 2009		 A W3C standard for forms written in XML and embedded in a host language, which keeps a form's presentation, purpose and data distinct. Separating purpose from presentation, which is the oldest form of the inversion Zane makes. More than forms: any surface, any channel. Zane's purpose is stated as verbs a user does, and checked.
VoiceXML 2.0 and 2.1
VoiceXML 2.0 and VoiceXML 2.1		 A markup language for spoken, voice-driven dialogs: synthesized speech, recorded audio, speech and keypad input, and calls, aimed at bringing web-style development to interactive voice response (W3C Recommendations; 2.1 in 2007). A real standard for one channel. Zane's voice carriage was derived by reasoning about the channel, not from this, and its own file says that first cut is the likeliest to move. A check across channels: what a declaration promises must be carriable in the channel it names. VoiceXML describes the dialog; it is not described here as refusing a promise.
SCXML and statecharts
W3C Recommendation, 2015		 A state-machine based execution environment derived from CCXML and Harel state tables. Its abstract does not mention interfaces or dialogs. State machines as a precise way to say what is reachable from where. Rights stated over reachability: an act with no undo, a flow with no exit. Zane does not run a state machine, and the page claims no overlap beyond reachability.

The sources left out on purpose, and the parts that were not read

Left out on purpose. ISO/IEC 24744 sometimes appears in lists of model-based approaches. Its published scope is a metamodel for defining software-engineering development methodologies, not user interfaces, so it has no row. The standard's page at ISO states that scope.

Not read. Apple's documentation pages build themselves in the browser, so the SwiftUI row rests on an overview and a search, as its cell says. The XForms, VoiceXML and SCXML specifications are long, and they were read through their abstracts and status sections.

A row that over-reads one of these sources is corrected from the source.
