Use · build · you ship business software

The build workflow puts the law into a project and makes the CI build fail when the verifier refuses a declaration.

The build workflow puts Zane into a software project: the team declares each surface before drawing it, pins the law as a hash, fails the build on a refusal, and measures what the browser actually paints. The workflow prevents a declaration that the law refuses from passing the CI. Nothing in it needs more than Node and a browser.

Writing a surface's declaration before drawing the surface

Before wireframes harden, you write the surface's .zane declaration: which intents it satisfies, and what stays always reachable. A few minutes of declaration replace a meeting about taste: the design review reads SATISFIES [SELECT, CONFIRM, ACT] and asks one question, is that what the operator is actually doing?, instead of debating paddings.

// specs/checkout.zane — written at the whiteboard, checked at the desk
DEFINE WIZARD checkout (
  SATISFIES [SELECT, CONFIRM, ACT],
  ALWAYS_REACHABLE [CANCEL, EXIT]
)
$ node tools/zane/cli.js check checkout.zane
checkout.zane:2  error  MISSING_UNDO  checkout
    An act declares no way back: SATISFIES holds ACT, ALWAYS_REACHABLE lacks UNDO.
    Rule 79 · The Undo Covenant · Article IV · the right to reverse

1 error(s), 0 warning(s) across 1 file(s) at level 2

The output above comes from a real run, and this site's own check re-runs it. The wizard has an exit and a way to cancel, and the law still refuses it, because it acts and promises no undo. The verifier ships in this repository and runs on Node alone. It reads its contract and its citations from the law rather than hardcoding them.

Level two, the default level, is what a declaration alone can decide. A check that needs a fact a declaration does not hold (the entities, the actors, the state, the elements of a surface) is skipped unless you hand it a symbol table with --symbols, and an undecidable check stays silent and is never a pass. A tool that computes that table from a host project is not built, as the last section says.

Pinning the law as a hash, not only as a version

A version says which edition you meant, and a hash proves that the bytes you hold are that edition. You vendor the files the protocol manifest names (the law, the language documents, the refusal contract, the two axes and the proof), record protocol/MANIFEST.json beside them, and make one command a step of your build:

$ node tools/zane/pack.js --check

With this step, conforms to Zane v3.14 becomes a claim that your CI can refute. Rule numbers are stable forever: a retired number is never reused, so a finding that cites Rule 79 means the same thing in ten years. The protocol pack says what to vendor and what you may and may not claim.

Making the CI build fail when the verifier refuses a declaration

The verifier exits non-zero when any declaration is refused, and it exits zero when there are only warnings. You run it over your specifications in CI:

$ node tools/zane/cli.js check specs/*.zane
$ node tools/zane/cli.js check specs/*.zane --json   # for a machine to read

The contract names 37 diagnostics at 4 conformance levels, and every finding carries the rule, article or right it rests on. The suite that proves any implementation agrees, 73 fixtures with known verdicts, is in conformance/.

Measuring the painted page with the UI audit

A declaration is not enough, because a page can be lawful on paper and unlawful in the browser. You serve your application and point the UI audit at it, one path per line, on any same-origin pages, and nothing leaves your browser. The audit measures what static analysis cannot see: computed text sizes, true contrast against the composited background, the trail, the room before scrollbars, the navigation bars against each other and the menu against the tree. The audit reports a colour it cannot read as not decided, names the colour, and never skips it. It exports a Markdown report in which each finding cites its rule.

You run the audit in every culture you ship, because a page can be lawful in one palette and unlawful in another. This site audits itself that way before it ships.

Proposing a new rule with evidence from your project

The law grows in one way only (Article VII): from real usage, operator feedback and documented failure. If your project hits a recurring defect that the law does not name, you record it as the law records its own defects: what happened, where, how it was corrected, why it generalizes, and whether a reviewer could decide it yes or no. Every rule carries an evidence field that says where the rule came from, and fashion, trends and developer convenience are not admissible as evidence. The amendment docket shows how a pass is ruled.

Parts of the build workflow that are held or designed, not built

This section states each missing part as held or designed, and not as promised.

  • Cross-pillar symbols are not computed. The verifier accepts a symbol table that you supply, and building one from a host project's other pillars is the open half of level three, which is unchanged.
  • One violation belongs to the audit, not to the verifier. LAYOUT_DISPLACEMENT is a fact about a painted page, so it has no fixture by design.
  • The AI-interaction jurisdiction is not written. The law has no rules for the chat stream, and no endpoint serves the law to an agent while it works. The roadmap keeps the account.
  • The Second Founding is proposed, not ratified. It argues for a wider design and its own rulings, and the law you pin is the law described above, not that document.
