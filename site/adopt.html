Use · which way in is yours

The Use section describes four ways to use Zane on an interface you already have, and where each way stops.

This section shows how to use Zane on what you already have: a web application in production, a mobile app, an interface with no screen such as a voice line or an agent, or your own language and framework. Each way in is a workflow on a real case, and it lets a person know what Zane gives today and what it does not before adopting it.

The four ways to use Zane, one card for each

Using Zane on a web application

You declare the application's surfaces, run the verifier, and then run the UI audit on the live pages. The Web apps page works through a real case: the navigation of a site this project does not own.

Using Zane on a mobile app

A mobile app has no page to measure. You declare its screens, reduce a screenshot to facts, and judge those facts. The Mobile apps page says what runs today and what has never run.

A voice line, a status chime and an agent that a machine drives are interfaces with no screen. The Beyond screens page says what the verifier decides in each channel and where the law is silent.

Using Zane in the stack you choose

You can build with Zane in your CI, make a generator declare intent before it draws, vendor the law inside Softanza, or port Zane to another language.

Your stack →

The Comparison and Why a law pages give the reasons for Zane and the case against the practices you already use. The status board lists, part by part, what is built, what is designed and what is held.

What the four ways to use Zane have in common

  • All four ways use one law, stored as data. The law holds 123 rules in one versioned file, v3.14.
  • All four ways use one refusal contract. The contract has 37 diagnostics, and each diagnostic is bound to the rule, article or right it enforces.
  • All four ways use one proof. The proof is 73 fixtures with known verdicts, which let an implementation prove that it agrees with the law instead of asserting it.
  • Zane needs Node and a browser today, and nothing else. A single file that needs neither is designed and not built.

Parts of the four ways that are not built or not run yet

  • The screenshot audit has a written fact schema and a checker, but no screenshot of a real application has been run through it, and no person has looked at one.
  • Rules for haptic, luminous, signage, spatial and terminal channels are held until a product that ships in one of these channels is named.
  • The wider design, called the Second Founding, is proposed, not ratified, and nothing on this page rests on it.
