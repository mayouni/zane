The contract · one law, three phases of your project

Deploy the law in your project

Zui deploys inside any software project — no framework to swap, no dependency to take. The declaration is plain text beside your code; the law is one JSON file with a stable schema; the audit runs in a browser. Here is the whole contract, phase by phase: what it does at design time, in development, and at runtime — and what you can start this afternoon.

In design — declare before you draw

Before wireframes harden, write the surface's .zui declaration: which intents it satisfies, what stays always reachable, which entities are visible to whom. Ten minutes of declaration replaces a meeting of taste: the design review reads SATISFIES [SELECT, CONFIRM, ACT] and asks one question — is that what the operator is actually doing? — instead of debating paddings.

// specs/checkout.zui — written at the whiteboard, checked at the desk
DEFINE WIZARD checkout (
  SATISFIES [SELECT, CONFIRM, ACT],
  ALWAYS_REACHABLE [CANCEL, EXIT]
)

Structure is refused early — a wizard with no EXIT should die on the whiteboard, not in the sprint. Stated plainly: the grammar parses today in the reference implementation (a consumer), which enforces four Zui diagnostics; the structural refusals are specified and are M3's work. Until the zui CLI ships, the declaration is still worth writing — it is the design document your team and your generator are held to, and an AI assistant given the law can already check it by hand.

In development — pin, lint, gate

Vendor rules.json into your repository and record the version. Your build now has a fact, not an opinion: conforms to Zui v3.13. Numbers are stable forever — retired numbers are never reused — so a finding that cites Rule 79 means the same thing in ten years.

$ curl -O https://…/constitution/rules.json
$ git add vendor/zui/rules.json
$ git commit -m "pin Zui v3.13"

Then make the law a gate, not a poster: lint declarations and markup against the pinned file in CI, and fail the build on machine-tier violations. Zing's zing check is the first conforming linter and the working model — every finding cites its rule number.

Holding your generator to it works today, with any capable AI assistant: put rules.json in its context, instruct it to declare intent before rendering and to cite the rules it obeyed, then close the loop with the audit's report:

You are building under the Zui Constitution (rules.json attached).
Declare each surface in .zui before rendering it. Every screen must
conform; cite the rule numbers you obeyed. Here is the audit report
of your last attempt — fix every finding, by number: 2 violations
[Rule 105, Rule 114]

The generator now has what it never had before: a written law it can be held to, and a measurement it cannot argue with.

At runtime — measure the paint

Serve your application and point the UI audit at it — one path per line, any same-origin pages, nothing leaves your browser. It measures what static analysis cannot see: computed text sizes, true contrast against the composited background, the trail, the room before scrollbars, the menu against the tree — and exports a Markdown report, each violation citing its rule number.

Run it in every theme you ship — a page can be lawful in one palette and unlawful in another. This site audits itself, in both vibes, before any page ships; the audit once caught its own defect doing so. Designed next on this front: a runtime guard that watches the projection's guarantees live — no dropped UNDO, no hidden action — and the MCP surface (M5) that serves the law to agents while they operate.

Amend with evidence

The law grows one way only (Article VII): real usage, operator feedback, documented failure. If your project hits a recurring defect the law does not name, record it the way the harvest records were kept — what happened, where, how it was corrected, why it generalizes, and whether a reviewer could decide it yes-or-no. That record is an amendment candidate. Fashion, trends, and developer convenience are not admissible; every rule above 104 entered exactly this way.

The road

What adoption will look like as the instruments land — stated as design, not as promise: M3, the zui verifier CLI — now open, with a decision document that audits what the reference implementation actually has and sequences the work: the language spec and conformance fixtures first, so any implementation in any language can prove agreement. M4, the intent→widget projection tables as data, checkable like the rules themselves. M5, the AI-interaction jurisdiction: laws for the chat stream, consent surfaces, and the MCP endpoint that serves all of it to generators. The details live in the roadmap.
