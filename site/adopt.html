Use · which way in is yours

The Use section describes four ways into Zane from an interface you already have, and where each way stops.

This section shows four ways into Zane from what you already have: a web application in production, a mobile app, an interface with no screen such as a voice line or an agent, or your own language and framework. Each way in is a workflow on a real case, and it lets a person know what Zane gives today and what it does not before adopting it.

The four ways to use Zane, one card for each

Using Zane on a web application

You declare the application's surfaces, run the verifier, and then run the UI audit on the live pages. The Web apps page works through a real case: the navigation of a site this project does not own.

What the four ways to use Zane have in common

  • All four ways use one law, stored as data. The law holds 123 rules in one versioned file, v3.16.
  • All four ways use one refusal contract. The contract has 40 diagnostics, and each diagnostic is bound to the rule, article or right it enforces.
  • All four ways use one proof. The proof is 77 fixtures with known verdicts, which let an implementation prove that it agrees with the law instead of asserting it.
  • Zane needs one file and a browser today, and nothing else. The file, zane, is version 0.1.0, for Windows, Linux and macOS (tested on Windows and Linux; built for macOS), on its release page.

How the four ways relate to the screenshot audit, the channels and the wider design

  • The screenshot audit has a written fact schema and a checker that decides, from a screenshot's facts, the rules a screenshot can decide.
  • Rules for haptic, luminous, signage, spatial and terminal channels are written when a product that ships in one of these channels is named.
  • This page rests on the ratified law. The wider design, called the Second Founding, is a proposal beside it.
